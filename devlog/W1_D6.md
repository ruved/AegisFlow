# W1 D6 — Evaluation Runner and Baseline E0

## Objective

Add a reproducible local golden-set evaluation runner that uses the existing
retrieval and generation path, captures ranked evidence and provider token usage,
and records an initial baseline in `results/baseline_E0.csv`.

## Dataset and configuration

- Dataset: `data/eval/golden_v0.jsonl`, the version-controlled W1 D4 set; 30
  question IDs (`G001`–`G030`) with expected filenames, document sections, and
  key facts drawn from the project corpus.
- Models: `nomic-embed-text:latest` for query embeddings and `gemma3:4b` for
  grounded generation, served by the local Ollama instance.
- Vector store: existing persistent collection at `chroma_db`.
- Retrieval: dense top-3 (`k=3`), three repetitions per question; 90 attempted
  full RAG runs.
- Reproduce with: `uv run python evals/run_eval.py --runs 3 --k 3`

## Measured baseline

The command above completed against the existing local models and collection.
All 30 questions had three successful runs; there were 0 failed questions and
0 failed runs.

| Questions excluded from Recall@3 | 5 (no expected gold source) |

Prompt and completion token counts came from Ollama response usage fields. For
each question, token counts in the CSV are the median of the provider counts from
successful runs; aggregate averages use the available per-question medians.

## Metric definitions and measurement boundary

- Source Recall@k is the number of distinct expected source filenames returned
  among the first `k` ranked chunks, divided by the number of distinct expected
  source filenames. It is source-level recall, not chunk-level recall or proof
  that a specific fact was retrieved. Paths are normalized to `/` separators and
  directory components are retained.
- Questions with no expected gold sources are recorded with a blank per-question
  recall and excluded from mean Recall@k. They remain in latency and answer
  reporting.
- Each run's latency uses a monotonic clock around the complete existing
  generation service call: query embedding, Chroma retrieval, and chat
  generation. The first run is included and can include model loading.
- Each CSV row records the median latency of its successful repetitions. The
  aggregate median and P95 are calculated across those per-question medians. P95
  uses nearest rank and is reported only with at least 20 successful questions.
- The answer and retrieved chunks are from the last successful run. All run
  latencies and failures are kept in JSON-encoded CSV cells. A failed run does
  not become an answer; the runner continues with later runs and questions.
- Ollama output and timings are not deterministic, even when the command,
  dataset, and row order are unchanged.

## Interpretation and limitations

The measured Recall@3 of 0.000 reflects the state of the collection at evaluation
time: `chroma_db` contained only two chunks, sourced from `architecture.md` and
`ingestion.md`. All 30 questions retrieved those same sample sources, while the
gold set expects material from `data/corpus` (runbooks, postmortems, service
documents, and incident logs). A representative Order Service answer correctly
said the retrieved context did not establish the database-connection facts. This
baseline therefore measures the current retrieval/generation path against an
under-populated, mismatched index; it is not a quality estimate for a fully
ingested corpus.

The current ingestion command defaults to `docs/rag_samples`, which explains the
two indexed sample sources. This evaluation did not mutate or rebuild the
existing collection. Before interpreting E0 as corpus retrieval performance,
ingest the intended `data/corpus` into a separate, explicitly selected store,
then rerun the same dataset, model settings, `k`, and run count. Compare the new
Recall@3, answer evidence, and latency against this recorded result.

Correctness is not automatically scored. The columns `key_facts_covered`,
`correctness_grade`, and `correctness_notes` are blank for all initial rows.
Manually review each answer and its retrieved chunks before filling them. Rubric:

- `0`: Incorrect, unsupported, or no meaningful answer.
- `1`: Mostly incorrect or misses nearly all key facts.
- `2`: Partially correct but misses important facts.
- `3`: Mostly correct with minor omissions.
- `4`: Correct and covers the expected key facts.
- `5`: Fully correct, complete for the question, and appropriately grounded.

The runner preserves these manual grading cells for matching question IDs when
the CSV is regenerated. Do not treat an automated key-fact text match as a
semantic correctness judgment.

## Output validation

`results/baseline_E0.csv` contains 30 unique question rows and all required
columns. CSV quoting round-tripped successfully, and all JSON-encoded source,
chunk, and run-latency cells parsed. All rows have blank grading cells; no answer
or evidence was truncated by the runner.
